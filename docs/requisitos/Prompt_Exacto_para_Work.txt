Quiero que construyas el MVP completo de la aplicación CrossEd tomando como fuente principal y obligatoria el archivo adjunto `CrossEd_SDD_Work_v1.1.md` y utilizando también como referencia los archivos Docker adjuntos.

El SDD debe considerarse la fuente de verdad funcional y técnica del proyecto. No simplifiques reglas, no cambies decisiones de arquitectura y no reemplaces comportamientos definidos en el documento sin justificarlo claramente.

OBJETIVO
Construir una aplicación web educativa multijugador de crucigramas, con frontend responsive y backend Java, lista para ejecutar localmente, contenerizada con Docker y preparada para un despliegue posterior.

REQUISITOS TÉCNICOS PRINCIPALES
- Backend: Java 21 LTS.
- Spring Boot 3.x.
- Maven.
- Lombok.
- Spring Web.
- Spring Validation.
- Spring WebSocket + STOMP.
- Spring AI.
- Spring Data Redis.
- Frontend: React / Next.js + TypeScript.
- Arquitectura: monolito modular con capas dentro de cada módulo.
- Nombres de clases, métodos, variables y paquetes propios del proyecto en español siempre que sea técnicamente razonable.
- Inyección con `@Autowired` por campo.
- Mappers manuales usando Lombok `@Builder`; no MapStruct.
- Comentarios breves y conceptuales en español.
- REST para operaciones discretas y WebSocket para notificaciones en tiempo real.
- Redis para estado temporal; no crear una base persistente de usuarios para el MVP.

FUNCIONALIDAD
Implementá todo lo definido en el SDD, incluyendo creación de partidas, generación de conceptos mediante IA, generación y validación matricial del crucigrama, edición previa por profesor, registro temporal de alumnos, máximo 60 participantes, juego en tiempo real, ranking, correo, seguridad temporal por tokens, desconexiones, heartbeat, avisos de 3 y 1 minuto, experiencia visual del conejito, mensajes humorísticos, cierre de partida y limpieza de sesión.

IA
- OpenAI como proveedor principal.
- Un reintento corto si la primera respuesta falla o no cumple la estructura.
- Gemini como respaldo si OpenAI sigue fallando.
- No ejecutar ambos proveedores simultáneamente para la misma solicitud.
- La IA selecciona conceptos y definiciones; no decide la geometría final.

CRUCIGRAMA
- Usar matriz interna.
- Cada intersección debe compartir exactamente la misma letra en una única celda física.
- Una celda de cruce horizontal + vertical no puede recibir una tercera palabra.
- No permitir palabras paralelas pegadas, falsos cruces, palabras accidentales o solapamientos inválidos.
- Todas las palabras deben formar un único componente conectado.
- Máximo de cruces: 1-4 letras = 1; 5-7 letras = 2; 8 o más = 3.
- Preferir cruces en segunda, penúltima o última letra de la palabra nueva, sin hacerlo obligatorio.
- Generar más conceptos candidatos que los solicitados para mejorar las opciones geométricas.
- Si no se puede usar la cantidad solicitada, reducir gradualmente hasta el máximo válido; mínimo 5 palabras.
- Antes de aceptar cualquier tablero debe aprobarlo `ValidadorCrucigrama`.

SEGURIDAD
- Profesor y alumno deben tener tokens temporales distintos.
- No enviar jamás la palabra correcta al frontend del alumno.
- El backend es la fuente de verdad para puntaje, intentos, tiempo, progreso y estado.
- No confiar en puntajes o estados enviados por el navegador.
- No exponer API keys, claves SMTP, tokens, stack traces ni secretos en logs.
- Usar variables de entorno para secretos.

DESCONEXIONES
- Heartbeat aproximado cada 5 segundos.
- Tolerancia aproximada de 15 segundos.
- Si un alumno deja de responder, eliminarlo del listado activo y eliminar su progreso.
- Si vuelve, registrarlo como un jugador nuevo.
- El tiempo global de la partida no se reinicia.
- Cambiar de pestaña no elimina al alumno: solo marca `pantallaActiva=false` para la vista del profesor.

TIEMPO
- El cronómetro es visible solamente para el profesor.
- Los alumnos no ven tiempo restante.
- Enviar eventos y avisos cuando falten 3 minutos y 1 minuto.
- El backend controla `fechaHoraInicio` y `fechaHoraFin`.

DOCKER E INFRAESTRUCTURA
La aplicación debe quedar contenerizada desde esta primera versión.

Creá y verificá:
- `backend/Dockerfile` con build multi-stage Maven + Java 21.
- `backend/.dockerignore`.
- `frontend/Dockerfile` multi-stage para Next.js.
- `frontend/.dockerignore`.
- `docker-compose.yml` en la raíz para levantar frontend, backend y Redis.
- `.env.example` sin secretos reales.
- health check del backend, preferentemente mediante Spring Boot Actuator en `/actuator/health`.
- health check de Redis.
- volumen local de Redis para desarrollo.
- CORS configurable por variable de entorno.
- URL REST y WebSocket del frontend configurables por entorno.
- `ws://` en local y preparado para `wss://` en producción.

Los archivos Docker adjuntos son referencias. Adaptalos a la estructura real que generes y corregí cualquier detalle necesario para que funcionen de verdad.

El resultado debe poder iniciarse desde la raíz del repositorio con:

`docker compose up --build`

Y debe verificarse que:
- frontend funcione en `http://localhost:3000`;
- backend funcione en `http://localhost:8080`;
- health check responda correctamente;
- backend se conecte a Redis usando el nombre de servicio de Compose;
- REST y WebSocket funcionen entre frontend y backend.

PRUEBAS OBLIGATORIAS
Creá pruebas unitarias y/o de integración que garanticen especialmente:
- cruce correcto en la misma celda;
- coincidencia exacta de letras;
- no reutilización de una intersección;
- límites de cruces por longitud;
- ausencia de contactos laterales inválidos;
- conectividad total del crucigrama;
- reducción de cantidad de palabras si no puede organizarse la cantidad solicitada;
- alumno no puede ejecutar operaciones de profesor;
- respuesta correcta no aparece en payload de alumno;
- desconexión elimina al jugador luego de la tolerancia;
- reingreso crea un jugador nuevo;
- tiempo global no se reinicia;
- alertas de 3 y 1 minuto;
- fallo de correo no impide finalizar una partida.
